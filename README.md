# HODIE

**Today. Not tomorrow.**

HODIE is a personal, local-first English learning environment designed to turn English from something postponed into a usable communication skill.

It is not being built as a catalogue of lessons or as a clone of a language-learning app. Its central purpose is:

> **After using HODIE for months, can Peters communicate better in English?**

Everything in the architecture, pedagogy, content, interface and future AI layer must answer that question.

---

## 1. The North Star

HODIE exists because knowing English and being able to use English are not the same thing.

The system optimizes for:

    USE ENGLISH → COMMUNICATE → EVIDENCE → GAP → PRACTICE → RETRY → TRANSFER → RETAIN

The product does not optimize primarily for lesson count, XP, streaks, a single global score, artificial completion, mandatory AI, or a course that ends at B1.

The permanent question is whether sustained use produces better real-world communication.

---

## 2. Product philosophy

### Today. Not tomorrow.

The name HODIE comes from Latin for “today” and from the devotional tradition associated with Saint Expeditus, in which the raven says Cras (“tomorrow”) and the response is Hodie (“today”). This is treated as a cultural/devotional tradition, not as established historical fact.

The idea fits the learning problem:

> English is not a project to postpone. It is a skill to use today.

### Core principles

1. Use over memorization.
2. Communication over isolated language resources.
3. Evidence over assumptions.
4. Progress over lesson count.
5. Errors are information.
6. Feedback should lead to action.
7. Retry when retry is useful.
8. Support should decrease as autonomy increases.
9. The same capability should return in new contexts.
10. Retention is maintenance, not punishment.
11. Confidence is measured separately from performance.
12. AI is a provider, not the owner of learning.
13. Local-first is the default.
14. The interface is a means to learning.
15. Less clicking. More English.

## 3. What HODIE is

HODIE is an adaptive personal learning environment with several connected learning experiences:

    HODIE
      ↓
    REAL-WORLD LANGUAGE USE
      ├── PRACTICE
      ├── CONVERSATION
      └── SIMULATION
              ↓
       EXPERIENCE ENGINE
              ↓
       FEEDBACK / ERRORS / REPAIR
              ↓
        EVIDENCE BOUNDARY
              ↓
       PROGRESS / RETENTION / TRANSFER
              ↓
       LEARNING ORCHESTRATOR
              ↓
          NEXT ACTION

The activities, conversations, simulations, review system and future AI are not separate products. They are different ways of moving the same learner through the same learning system.

---

## 4. KNOW → USE → PRODUCE → INTERACT → TRANSFER

HODIE distinguishes:

- KNOW — recognize or understand language.
- USE — use it in a controlled or supported situation.
- PRODUCE — generate language independently.
- INTERACT — respond, ask, clarify and repair.
- TRANSFER — perform the capability in another meaningful context.

A correct multiple-choice answer is useful evidence of recognition. It is not automatically evidence of communicative mastery.

## 6. Target level

HODIE starts from an A2 learner profile and aims first for functional B1-aligned communication.

This is not an official CEFR certification.

The system uses CEFR descriptors as its primary pedagogical reference, with Cambridge B1 Preliminary and British Council B1 material as complementary practical references.

The planned progression is:

    A2 → A2+ → B1 → future B1+ / B2

There is deliberately no final course-completed state.

After B1, HODIE should continue developing fluency, precision, interaction, transfer, range and confidence.

## 7. Evidence-based progression

The core loop is:

    Can-Do
       ↓
      TRY
       ↓
    EVIDENCE
       ↓
      GAP
       ↓
    RECOVERY / PRACTICE
       ↓
      RETRY
       ↓
    PROGRESS
       ↓
    TRANSFER
       ↓
    RETENTION

Evidence levels:

- attempt
- supported
- independent
- consistent
- transfer

Can-Do status:

- notStarted
- emerging
- developing
- functional
- consolidated
- transferred

Functional performance does not automatically mean strong mastery.

Consolidation requires repeated independent evidence in different contexts.

Confidence is diagnostic. It must not hide successful observable performance.

---

## 8. Progression and retention

HODIE separates two questions.

### Progression

What can the learner demonstrate increasingly independently?

### Retention

Which previously developed capacities need to be used again?

Time does not automatically erase mastery.

Retention states are:

- unscheduled
- current
- due
- atRisk

atRisk means maintenance is overdue. It does not mean the capability has been lost.

The system can re-test a capability and use new evidence to preserve, reinforce or recover it.

This is why:

    activity ends ≠ capability ends

---

## 9. Transfer

A capability becomes stronger when it survives context changes.

For example:

    “I can talk about my work.”
             ↓
        ┌────┼────┐
      school  meeting  interview
             ↓
       robotics conference

HODIE records context and transfer evidence.

The Transfer Engine looks for:

- independent performance;
- repeated evidence;
- more than one context;
- explicit transfer evidence when available.

The same Can-Do can therefore return many times without being considered wasted repetition.

---

## 10. Learning memory

HODIE needs learning memory, not merely conversation history.

The longitudinal model tracks:

- evidence timeline;
- active Can-Dos;
- skill coverage;
- recurring errors;
- transfer contexts;
- current status;
- retention state;
- recent performance.

The Error Memory layer aggregates recurring problems by type, target, frequency, last occurrence, context and examples.

This allows Review to be driven by evidence rather than by a generic “review lesson”.

Relevant contexts include:

- technology;

- education;
- STEAM;
- students;

- school;
- professional communication;
- meetings;

## 15. Experience modes

Practice, conversation and simulation are distinct experiences over the same learning system.

### Practice

Short, focused actions.

### Conversation

Interaction with a conversational partner.

Current architecture:

    Guided Open Conversation
              ↓
    Adaptive Guided Conversation
              ↓
        AI Conversation

### Simulation

Realistic role-based situations:

- interview;
- teacher/classroom scenario;
- presentation;
- professional interaction;
- technology and robotics scenarios.

Future experience types can include:

- challenge;
- project;
- assessment/checkpoint;
- reflection;
- real-world task;
- fluency session;
- transfer session.

Experience completion alone does not mutate authoritative progress.

---

## 16. Conversation

Conversation is a central differentiator.

A useful conversation is not a single question followed by the end.

It should be able to:

- ask follow-up questions;
- react to the learner’s answer;
- correct when correction is useful;
- maintain a context;
- invite retry;
- observe communication;
- avoid interrupting every sentence.

Possible interaction policies include:

- Fluency mode — speak first, feedback later.
- Correction mode — immediate correction.
- Conversation mode — interrupt only for important problems.
- Interview mode — HODIE acts as interviewer.
- Teacher mode — learner explains.
- Student mode — HODIE acts as student.
- Presentation mode — learner presents.
- Role-play — a realistic scenario.

The current rule-based layer is intentionally limited but useful. It establishes the experience contract without requiring an external AI service.

---

## 17. Communication repair

Real communication includes misunderstandings.

HODIE therefore treats repair as a skill.

Repair strategies include:

- clarification;
- confirmation;
- reformulation;
- continuation.

Examples:

> “Could you say that again?”

> “Do you mean...?”

> “Let me say that another way.”

> “The important thing is...”

A learner who can repair communication is more capable than a learner who only produces isolated correct sentences.

---

## 18. Feedback

Feedback follows:

> Explain in the learner’s strongest language; practice and demonstrate competence in English.

Current policy:

- A2: bilingual by default.
- A2+: English-first with Spanish support.
- B1: English-first, Spanish when useful.

Feedback is:

- immediate when useful;
- concise;
- actionable;
- limited to priority corrections;
- followed by retry when a correction materially affects the target.

HODIE deliberately avoids over-correcting fluency tasks.

The current normal display allows a maximum of two priority corrections.

---

## 19. Evidence Boundary

This is a fundamental architectural boundary.

A practice interaction can generate observations.

Only an explicit assessment activity inside an authorized session can generate authoritative progress evidence.

The intended flow is:

    Practice
       ↓
    observations
       ↓
    Feedback
       ↓
    optional retry

    Assessment activity
       ↓
    Evidence Boundary
       ↓
    Learning Engine
       ↓
    Progress / Retention / Transfer

Conversation, simulation and future AI providers must not silently mutate progress.

---

## 20. Session architecture

A learning session follows:

    planned
      ↓
    started
      ↓
    awaiting-evidence
      ↓
    completed
      ↓
    register-evidence
      ↓
    retry-required → started

or:

    completed → next

The Session Runner is the executable orchestration path.

The former direct learning-cycle path was removed because it could bypass session state and the Evidence Boundary.

---

## 21. Adaptive orchestration

HODIE should not simply ask “What is lesson 27?”

It should ask:

> **Given the learner’s evidence, context, retention state, errors, transfer and goals, what is the most useful next action?**

The Learning Orchestrator considers:

1. retention risk;
2. recent errors;
3. learner context;
4. communicative needs;
5. speaking/listening opportunities;
6. simulation readiness;
7. progression;
8. next executable activity.

The Adaptive Planner adds:

- priority;
- status need;
- skill balance;
- review due;
- recent gaps;
- context match;
- progression fit;
- retention risk.

The planner is a decision layer, not a lesson list.

## 23. Session Composer and Learning Budget

HODIE adapts to available time.

| Mode | Time | Micro-actions | Experience turns |
|---|---:|---:|---:|
| Quick | 5 min | 3 | 0 |
| Standard | 15 min | 5 | 3 |
| Deep | 30 min | 7 | 5 |

The Session Composer can combine:

- review;
- production;
- conversation;
- reflection.

A 5-minute session should not become a miniature course. A 30-minute session should not become a pile of disconnected exercises.

## 24. Multimodal learning

HODIE matches interaction to the skill.

| Experience | Primary interaction |
|---|---|
| Speaking | voice |
| Writing | writing |
| Listening | audio |
| Grammar | structure manipulation |
| Vocabulary | retrieval and use |
| Conversation | open interaction |
| Interview | role + objectives + dialogue |
| Simulation | situation + objectives + performance |

Important invariant:

    SPEAKING → voice interaction
    WRITING  → writing interaction
    LISTENING → audio input
    GRAMMAR → grammar interaction

A speaking task must not force typing simply because typing is easier to implement.

## 25. Audio and voice

HODIE supports:

- browser text-to-speech;
- normal/slow audio playback;
- browser speech recognition when available;
- typed fallback when speech recognition is unavailable.

Speech recognition is treated as capability-dependent.

Pronunciation scoring remains conservative until a reliable method exists.

## 26. AI architecture

AI is important for truly open, natural conversation, but it is not required for the core learning system.

HODIE therefore uses a provider abstraction:

    Conversation Engine
           ↓
    Conversation Provider
           ↓
      ┌──────────────┐
      │ Rule-based   │
      │ AI provider  │
      └──────────────┘

The future AI provider can add:

- free conversation;
- semantic follow-up;
- natural correction;
- open writing feedback;
- richer role-play;
- adaptive dialogue;
- personalized explanations.

But:

> **AI must never directly mutate progress.**

The future flow remains:

    AI
     ↓
    raw interaction / observations
     ↓
    Evidence Boundary
     ↓
    Learning Engine
     ↓
    Progress / Retention / Transfer

This protects the learning model from vendor lock-in and uncontrolled API cost.

Core practice remains useful without an external AI API.

## 27. Local-first architecture

The intended platform is:

- HTML;
- CSS;
- JavaScript;
- JSON;
- browser storage;
- Service Worker;
- GitHub Pages.

Current persistence uses local storage for progress and resumable state.

The architecture is prepared for a future IndexedDB migration where larger datasets or richer offline state justify it.

Core rules:

- core learning should work without an account;
- deterministic practice should not require a backend;
- ordinary micro-practice should not require an API call;
- external services are optional;
- learner data should remain under learner control.

---

## 28. PWA direction

The application is intended to become an installable Progressive Web App.

Target capabilities:

- installability;
- offline resources;
- cached learning content;
- resilient local progress;
- update-safe Service Worker;
- responsive mobile-first UI.

PWA infrastructure must not become a prerequisite for testing the pedagogical engine.

---

## 29. Mobile-first UX

The interface follows function rather than fashion.

Rules:

1. One primary action per screen.
2. Large touch targets.
3. Minimal typing when speaking/listening is intended.
4. Immediate feedback.
5. No unnecessary confirmation screens.
6. No unnecessary Next clicks when the next action is deterministic.
7. Resume interrupted practice.
8. Preserve progress locally.
9. Keep the learner oriented.
10. Make the recommended action obvious.
11. Allow focus changes without losing learning state.
12. Keep Spanish support close to the action at A2.
13. Use progressive disclosure.
14. Avoid decorative elements that compete with the task.

Ideal flow:

    OPEN HODIE
       ↓
    SEE TODAY'S ACTION
       ↓
    ACT
       ↓
    GET FEEDBACK
       ↓
    RETRY or CONTINUE

Not a long chain of menu and confirmation screens.

---

## 30. Accessibility and capability adaptation

The interface should adapt to device capability.

Examples:

- speech recognition available → voice interaction;
- unavailable → visible typing fallback;
- audio available → listening;
- reduced motion → avoid unnecessary animation;
- narrow screen → single-column action layout;
- keyboard → accessible controls and focus order.

Accessibility is part of functional UX.

## 34. Review

Review is not simply “repeat yesterday’s lesson”.

Review is driven by:

- repeated errors;
- weak dimensions;
- retention due date;
- retention risk;
- previous contexts;
- low-confidence performance;
- unresolved communication problems.

This makes maintenance evidence-driven.

---

## 35. Confidence

Confidence is transversal.

For example:

    performance = good
    confidence = low

and:

    performance = weak
    confidence = high

are different learning situations.

Confidence should influence support and future experience selection, but it should not erase observable evidence.

---

## 36. Reflection

Reflection is a lightweight learning layer, not a mandatory journal.

Possible prompts:

- What felt easy today?
- What was difficult?
- What expression do you want to use again?
- Where did you hesitate?
- What can you now say that you could not say before?

Reflection should help learner awareness without becoming administrative overhead.

## 37. Projects and real-world challenges

- explain a classroom activity;

- simulate a technology meeting;
- prepare for an interview;
- explain a STEAM project.

These experiences should reuse existing Can-Dos rather than create a parallel curriculum.

## 38. Longitudinal learning

HODIE is designed for months and years.

The longitudinal model therefore records:

- active Can-Dos;
- skill coverage;
- recurring errors;

- current status;
- retention state;
- recent performance.

This supports the central product question:

> **Is the learner becoming more capable over time?**

---

## 39. Privacy and data ownership

The intended architecture is local-first.

Future infrastructure should support:

- export;
- import/backup;
- explicit reset;
- versioned migrations;
- no hidden progress mutation;
- no provider-owned learner profile;
- no requirement to send all learning activity to a server.

AI should receive only what is necessary for the requested interaction when an external provider is enabled.

---

## 40. Determinism and testing

The pedagogical engine should be deterministic wherever possible.

Tests use injected time where needed.

The application is split so that:

- learning logic can be tested without the browser;
- content can be validated without rendering;
- evidence can be tested without UI;
- provider interfaces can be tested without an AI API;
- the UI can be syntax-checked independently.

A green test suite is necessary but not sufficient.

The final criterion remains actual learning progress.

### Current runnable scope (v1)

The size of the Can-Do matrix is not the same as the amount of content already executable in the interface.

- **Can-Do descriptors:** 133 in the matrix.
- **Currently executable targets:** four A2 speaking targets, `SP-A2-01` through `SP-A2-04`.
- **Micro-practice:** 47 activities across those four targets; each target has mixed, speaking, listening and writing practice.
- **Conversation and simulation:** four rule-based experiences (one open conversation and three simulations).
- **Persistence:** progress and resumable sessions are stored locally in the browser.
- **Voice:** speech recognition depends on browser support and microphone permission; typing remains available as a fallback.
- **AI:** the provider interface exists, but an AI service is not wired into the app.
- **Not yet covered end-to-end:** the remaining 129 Can-Do descriptors, full B1 content coverage, and direct Reading/Pronunciation modes in the home interface.

The app should not imply that all 133 descriptors are already fully teachable. Expand content and tests before marking additional Can-Dos as executable.

## 42. Architectural invariants

### Invariant 1 — One objective
Everything exists to improve real English communication.

### Invariant 2 — Can-Do is the capability unit
Activities are not the curriculum unit.

### Invariant 3 — Evidence controls progress
Completion alone does not establish mastery.

### Invariant 4 — Evidence has a boundary
Practice, conversation and AI observations cannot silently mutate authoritative progress.

### Invariant 5 — Communication is primary
Grammar, vocabulary and pronunciation support communicative performance.

### Invariant 6 — Experiences must match the skill
Speaking should not become a typing task merely because typing is easier to implement.

### Invariant 7 — Context matters
The same capability should be reusable across contexts.

### Invariant 8 — Retention is not regression
Time creates review need, not automatic failure.

### Invariant 9 — AI is optional
The system remains useful without an external AI service.

### Invariant 10 — AI never owns progress
Only HODIE’s evidence and learning layers decide progression.

### Invariant 11 — Fewer clicks
Every extra interaction must justify its existence.

### Invariant 12 — No artificial ending
The system continues beyond B1.

### Invariant 13 — Testable architecture
Pedagogy and UI remain independently testable.

### Invariant 14 — Local-first
Core learning should not depend on accounts, servers or paid APIs.

## 47. The permanent question

When a future feature is proposed, ask:

1. Does it improve English communication?
2. Which learning capability does it improve?
3. What evidence would show that?
4. How does it connect to the existing learning model?
5. Does it reduce or increase unnecessary interaction?
6. Can it work locally?
7. If it uses AI, why is AI actually necessary?
8. Does it preserve the Evidence Boundary?
9. Does it support progression, retention or transfer?
10. Will it still make sense after months of use?

If the answer is unclear, the feature should not be added merely because it is technically interesting.

## 48. The HODIE principle

> **HODIE is not a collection of English exercises.**

> **It is a system that helps a learner decide what to do, do it in English, understand what happened, recover from difficulty, demonstrate real capability, transfer that capability to new situations, and keep it available through continued use.**

> **Today. Not tomorrow.**
